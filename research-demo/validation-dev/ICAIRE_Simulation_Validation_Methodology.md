## 0. What v1.2.3 already has, and what this methodology adds

This matters because two of the seven requested items (forecasting-baseline
comparison, rotation-recommendation evaluation) can be misread as "evaluate
the existing feature." They are not that. Re-checking the frozen source:

| Capability | Exists in v1.2.3? | Evidence |
|---|---|---|
| Rule-based, stateless-per-minute anomaly detection with a confirmation window | **Yes** | `matchEvents()`/`metrics()`, independently verified in `Verification_Rerun_Report.md` |
| A linear-regression forecast (`linearForecast`, last-4-readings OLS extrapolation) | **Yes**, but only as an internal *early-warning* signal inside the Simulation Lab/anomaly-detection tool, not as a dose forecast that is itself evaluated against ground truth | Line 1172: "**Prediction** = linear extrapolation of the last 4 readings... projecting a deviation at or above the elevated threshold within 3 minutes" |
| Worker-rotation *recommendation generation* (an algorithm that decides who should rotate, based on dose/risk) | **No.** The four "AI Recommendation" entries are static, hand-written example text | Line 1706: "a static, hand-written illustrative example entry for this prototype — it was not generated by the live detection engine or by any forecast"; lines 1541–1542 are literal hand-authored strings |
| A device-handoff "rotation" feature | **Yes, but it is a manual UI action, not a recommender** — `rotateDevice()` just re-binds a device ID to a different worker when a human clicks a button; it does not decide *who* should rotate or *when* | Lines 861–880, 1604–1612 |

**Consequence for this methodology:** items 3 and 4 below split into two
tracks:
- **Track A — evaluate what exists:** anomaly detection and the internal
  linear forecast, against the existing matching framework, extended to a
  statistically adequate sample. This is squarely in scope and needs no new
  algorithm.
- **Track B — define, for later implementation, how a not-yet-built dose
  forecaster and rotation recommender would be evaluated.** This is
  deliberately a specification, not a result. It exists so that once such
  an algorithm is implemented (a future stage, not this one), there is
  already an agreed, pre-registered evaluation protocol for it — which is
  itself good scientific practice (pre-registration prevents metric-shopping
  after the fact). No rotation or forecasting algorithm is implemented here.

## 1. Radiation exposure simulation — workers, rooms, procedures, shifts

**Reuse, not replace.** The existing scenario generator (`SCEN`/`SC` arrays,
`Ground_Truth_Scenarios_S1-S13.md` §§S1–S13) already parameterizes: a worker
id, a room, a `procMult` (procedure-dependent rate multiplier, currently
fixed at `1.0` in all 13 hand-authored scenarios), a measurement mode
(`personal` or `area`), a pattern (`flat`/`ramp`/`step`/`spikes`), and a
seed. The proposed simulation design keeps this exact object shape and
exact seeded-RNG mechanism, and widens three dimensions that are currently
fixed constants in the hand-authored set:

| Dimension | Current v1.2.3 (hand-authored S1–S13) | Proposed for the evaluation sample |
|---|---|---|
| Procedure multiplier (`procMult`) | Fixed at `1.0` in every scenario | Drawn per-run from a small, explicitly justified set of procedure classes (e.g., diagnostic fluoroscopy, interventional cath lab, CT, PET/CT), each with its own multiplier range — **range values require RSO/medical-physicist sign-off before use; none are proposed here as final**, see §7 |
| Shift / window length | Fixed at 60 minutes (one hour, matching the Simulation Lab's fixed 60-step loop) | Drawn from a small discrete set (e.g., 1 h / 4 h / 8 h / 12 h) to test whether detection/forecast performance degrades on longer, lower-event-density windows |
| Room/worker count per run | 1–3 workers per scenario, fixed assignment | A multi-worker roster per run (reusing the existing per-worker independence already validated in S6/S12), with room assignment randomized but seeded |

**What does not change:** the underlying per-minute rate-generation
mechanism (`seededSeries`-style noise around a baseline, inverse-square
modeling for area-mode workers, the four pattern types) is reused exactly
as implemented and verified — this proposal is about *sampling that
mechanism more broadly and more times*, not about replacing it with a
different simulator. Replacing the underlying physics/noise model is out of
scope; this is a validation-methodology document, not a re-engineering
proposal.

## 2. Ground-truth injection — radiation anomalies and sensor failures

**Reuse, not replace.** The existing `truth` (radiation events) and
`faults` (sensor failures: `missing`/`invalid`/`frozen`/`delayed`) arrays,
and the dual-layer `matchEvents()` scoring already verified for S1–S13, are
the ground-truth mechanism. The proposal is to generate these
programmatically per seed instead of hand-authoring 13 fixed cases:

- **Event taxonomy** (reused as-is): `ramp`, `step`, `spikes` — each with a
  start time, magnitude multiplier, and duration drawn from a declared
  range (not yet chosen — see §7 for why that choice needs expert input
  before being fixed).
- **Fault taxonomy** (reused as-is): the four existing fault kinds, with
  timing/duration/magnitude likewise drawn from a declared range rather
  than the 13 fixed windows currently hand-picked (e.g., S7's fixed 25–40,
  S10's fixed 15–50).
- **Formal ground-truth record schema**, generated alongside each
  simulated run (not stored only in hand-written scenario objects):
  `{run_id, seed, worker_id, truth_events:[{start,end,label}], fault_events:[{kind,start,end,params}]}`.
  This is a data-shape proposal only; it is the same information the
  existing engine already produces per scenario, made systematic instead of
  one-off.
- **What does not change:** the matching algorithm (`matchEvents()`, grace
  period, TP/FP/FN/precision/recall/F1 via `metrics()`) is reused exactly as
  verified — no new scoring logic is proposed.

## 3. Comparison against conventional threshold alerts and forecasting baselines

### 3a. Detection baselines (Track A — existing detector, new comparators)

| Baseline | Description | Status |
|---|---|---|
| **Baseline 0 — "always normal"** | Never alerts. A sanity floor: establishes the base rate of true events per scenario class, and gives every other method's recall a non-trivial denominator to beat. | To be implemented as a trivial comparator, not an "algorithm" |
| **Baseline 1 — stateless threshold, K=1 (no confirmation window)** | Already produced as one row of the existing `ref_sweep.py` grid (confirmation window = 1). | **Reuse directly** — no new code, just re-select this slice of the existing sweep output |
| **Baseline 2 — "conventional" moving-average threshold alarm** | A deliberately simple reference implementation in the style of a conventional radiation-safety threshold alarm (fixed-window moving average crossing a fixed multiple of baseline, no adaptive logic) — representing "what a non-ALARAD, off-the-shelf threshold alarm would do" | New, but intentionally simple/dumb reference code, not a competing product |
| **Candidate — ALARAD's confirmation-window detector at its documented operating point** | The existing engine, as verified. | Already implemented; no change |

This gives the paper an honest three-point comparison: a floor (Baseline 0),
a literal ablation of ALARAD's own confirmation-window feature (Baseline 1,
already computed), and an external-style reference (Baseline 2), rather
than only comparing ALARAD against itself at different settings.

### 3b. Forecasting baselines (Track A — the existing internal forecast, evaluated properly for the first time)

| Baseline | Description |
|---|---|
| **Persistence (naive)** | Forecast = last observed value. Standard minimum baseline for any time-series forecast claim. |
| **ALARAD's existing `linearForecast`** | OLS on the last 4 readings, as already implemented — evaluated here as a forecaster in its own right (predicted value vs. the simulator's known true future value), which the current engine does not do; today it is only used as an early-warning trigger, not scored for forecast accuracy. |
| **Simple exponential smoothing** | A second, slightly less naive conventional baseline, for a three-point comparison analogous to §3a. |

**Leakage note (previewed here, detailed in §6):** because this is
simulation, the true future value is always known — that must not leak into
the forecast input. Each forecaster sees only data strictly before its
prediction horizon; the true value is used only afterward, for scoring.

### 3c. Rotation-recommendation baseline (Track B — specification only, nothing implemented)

No rotation-recommendation algorithm exists in v1.2.3 (see §0) and none is
proposed for implementation in this document. What is proposed is the
**evaluation protocol a future recommender would have to pass**, defined
now so it cannot be loosened later to fit whatever gets built:

- **Reference rule** (not an "AI", a fixed policy, standing in for "what the
  static illustrative recommendations in v1.2.3 would amount to if made
  automatic"): rotate a worker out when projected cumulative dose crosses a
  declared fraction of the reference level — this is the same logic already
  present as prose in the two existing hand-written recommendation strings
  (lines 1541–1542), made mechanical.
- **Evaluation criteria for any future candidate recommender**, to be
  scored against the reference rule and against "no rotation" on simulated
  rosters: (1) reduction in cumulative dose at end of shift vs. no
  rotation, (2) fairness — variance of cumulative dose across workers on
  the same roster should not increase, (3) time-to-recommendation latency,
  (4) number of rotations recommended per shift (a cost; more rotations is
  not free). These four criteria are a specification to be reviewed, not a
  result.

## 4. Evaluation protocol per capability

| Capability | Track | Metrics | Ground truth source |
|---|---|---|---|
| Anomaly detection | A | Precision, recall, F1, detection latency (minutes from true window start to first flagged minute), false-positive rate on `truth: []` scenarios | `truth` arrays, existing `matchEvents()` |
| Data-quality/sensor-fault detection | A | Same metric set, independently, per §2 of `Ground_Truth_Scenarios_S1-S13.md` | `faults` arrays, existing dual-layer matching |

| Rotation recommendation | B — specification only | The four criteria in §3c | Not applicable yet — no run has been performed |

## 5. Scientific metrics, statistical analysis, and seed count

**Minimum 30 independent seeds per scenario class**, not 30 seeds total.
There are 13 scenario archetypes (S1–S13); treating each as its own class
(since they test materially different mechanisms — ramp vs. step vs.
multi-worker vs. each of the four fault kinds) gives a minimum evaluation
sample of **13 × 30 = 390 independent runs**, each with its own fresh seed,
none of which may be one of the 13 original hand-authored seeds (20260601
through 20260613) — those 13 are reserved as the **design set** (see §6)
and must never be counted in the statistical sample.

- **Per-class summary statistics:** mean and median precision/recall/F1 (and
  forecast MAE/RMSE/MAPE), with 95% confidence intervals computed by
  bootstrap resampling (appropriate given n=30 per class — not large enough
  for normal-approximation CIs to be assumed reliable without checking).
- **Paired comparison across methods:** for each scenario class, the
  candidate detector/forecaster and each baseline are run on the *same* 30
  seeds (paired design), so a paired test (e.g., Wilcoxon signed-rank,
  non-parametric and robust to the non-normal distributions these metrics
  typically have) is used rather than an unpaired test.
- **Multiple-comparison correction:** with 13 scenario classes × up to 3
  baselines per capability, a Holm–Bonferroni correction is applied across
  the family of comparisons being reported together, so the paper does not
  overstate significance from running many tests.
- **Effect sizes, not just p-values:** report the absolute precision/
  recall/F1/MAE differences alongside any significance test — a
  statistically significant but practically tiny difference should not be
  reported as if it were operationally meaningful.

## 6. Leakage-free evaluation and sensitivity testing

**Three-way seed separation** (the core anti-leakage control):

1. **Design set** — the 13 original hand-authored scenarios and seeds
   (20260601–20260613). These informed the existing engine's thresholds and
   behavior during its original development and are documented in
   `Ground_Truth_Scenarios_S1-S13.md`. They may continue to be used for
   illustration, regression testing, and the software-verification suites
   already covered in `Verification_Rerun_Report.md` — but **must never be
   reused as the statistical evaluation sample**, because the engine's
   existing behavior is already known to pass them; doing so would be
   circular.
2. **Tuning set** — a separate block of freshly seeded runs (count to be
   fixed before implementation, e.g. 10 seeds per class), used only if any
   baseline implementation needs a parameter choice (e.g., the moving-average
   window length for Baseline 2 in §3a). Any such choice is frozen after
   tuning and never revisited after seeing evaluation-set results.
3. **Evaluation set** — the ≥390 freshly seeded runs from §5, used only
   once, only for the final reported metrics. No parameter in any detector,
   forecaster, or baseline may be changed after evaluation-set results are
   seen; doing so and re-running would itself be a leakage violation.

**Forecast-specific leakage control** (per §3b): at every scored time step,
a forecaster receives only observations with timestamps strictly earlier
than the prediction target; the simulator's true generating parameters
(e.g., the exact ramp slope used to create the data) are never exposed to
any forecaster, only to the scorer, after the fact.

**Sensitivity testing:** extend the existing `ref_sweep.py` methodology
(already verified to independently reproduce 8,640 runs / 432 grid cells
across confirmation window K, noise level, and alert threshold) to the new
evaluation set, so performance is reported as a stability surface across
detector settings, not a single cherry-pickable operating point. Any claim
of "ALARAD detects X% of events" must be accompanied by how that figure
moves across the sweep grid, exactly as the existing sweep already does for
the design set.

**Reproducibility controls carried over from the verification stage:**
fixed, published seed lists (committed to the repository, not regenerated
ad hoc); explicit disclosure of the Chromium/browser-engine version used
for any suite that drives a real browser (per the version caveat already
recorded in `Verification_Rerun_Report.md`); SHA-256 of whatever file is
actually evaluated, recorded alongside every reported number.

## 7. Scientific assumptions, limitations, and required expert review

### Assumptions carried over from the existing engine (not newly introduced, but newly load-bearing once evaluated statistically)

- Inverse-square-law point-source approximation for area-monitor modeling —
  **the engine's own in-page text already discloses this is "only a limited
  point-source approximation; scatter in real rooms does not follow it"**
  (line 1170). Any forecast/detection result involving area-mode workers
  inherits this limitation.
- The detector and forecaster are both deterministic and rule-based (OLS
  linear regression, fixed thresholds) — confirmed in `Gap_Checklist.md` §1.
  No trained model, so no train/test split in the ML sense is needed for
  the *detector itself* — the seed separation in §6 is about evaluation
  sampling, not about preventing model overfitting.
- Synthetic noise (±5% on flat baselines, as implemented) stands in for
  real dosimeter measurement noise. Its realism relative to actual wearable
  dosimeter noise characteristics is unverified (`Gap_Checklist.md` §5).

### Limitations (restated from `Gap_Checklist.md`, directly relevant to this methodology)

- All ground truth, under both the existing 13 scenarios and the proposed
  ≥390-run evaluation sample, remains **synthetic and author-specified**,
  not derived from real wearable-sensor data or real hospital shift logs.
  This methodology improves the *statistical adequacy* of synthetic
  evaluation; it does not, by itself, close the "no real data" gap.
- No independent domain-expert (RSO/medical physicist) has reviewed or
  signed off on any of the *specific numeric ranges* this document leaves
  open (procedure-multiplier ranges in §1, event/fault magnitude-duration
  ranges in §2, forecast horizons in §4). This document deliberately leaves
  those as open parameters rather than inventing plausible-sounding numbers.
- The rotation-recommendation evaluation protocol (§3c, §4 Track B) has no
  implementation to test yet; its criteria are a pre-registration, not a
  validated methodology — they should themselves be reviewed before being
  treated as fixed.
- Reproducibility is currently qualified by the disclosed Chromium
  141-vs-153 version gap (`Verification_Rerun_Report.md` §2); any new
  evaluation run under this methodology should either close that gap or
  carry the same disclosure forward.

### Required expert review (gate before implementation, not an afterthought)

Before any code under this methodology is written, the following need
domain-expert input — **this document does not substitute for that
review**:

1. Procedure-class multiplier ranges (§1) — realistic rate multipliers per
   procedure type, from a radiation safety officer or medical physicist.
2. Event and fault magnitude/duration ranges to sample from (§2) — currently
   only the 13 hand-picked examples exist as precedent; a defensible
   sampling range needs domain input, not an engineering guess.
3. Clinically/operationally meaningful forecast horizons (§4) — "15
   minutes" above is a placeholder for discussion, not a chosen value.
4. The four rotation-recommendation evaluation criteria (§3c) — specifically
   whether fairness-across-workers and rotation-count-as-cost are the right
   criteria, and whether others (e.g., procedure continuity/handoff safety)
   are missing.
5. Sign-off that the overall three-tier baseline structure (§3a/§3b) fairly
   represents "conventional practice" as ICAIRE's methodology would expect
   it characterized, rather than this team's own framing of what counts as
   conventional.
